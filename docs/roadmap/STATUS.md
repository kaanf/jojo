## Decisions in force

- Strategy: Reuse > Port > Adapt > Build. Keep the Rust core and the SwiftUI app. Prefer native CLI subscriptions over API keys.
- Code sources: Vigla (Apache-2.0) and weft (owner's permission reported by the human on 2026-11-15; no written record in the project). Prompts and test cases from spec-kit, factory, commandcenter, fabro.
- Approvals: four kinds, no approve-all (spec, plan, push, PR).
- Repair: automatic, at most two tries, then a human hold. External actions are never retried automatically. Built in M4: the limit (0 to 2) and the cross-provider reviewer are set per project, from its newest revision; a review approves nothing.
- Executables: discovered automatically through the login shell's PATH and checked again before each run; version and digest recorded per run; a change is a warning, not a refusal (D3). Pinning with all three options restores the refusal.
- Feature Chat and the project record come before the demo.
- Escaped agent child processes are signalled after a freeze-and-check of PID and start time (E1). Inspection stays on `/bin/ps`; the system-call version is deferred to Phase 4 (E2).

- Design work: read `docs/design/` before the canvas. `JOJO_SNAPSHOT_DIR=<directory> swift test --filter DesignShellTests` (in `macos/JojoApp`) writes the shell, every status component and shared surface, and each redesigned screen in its states as PNG files in dark and light, off screen; look at them instead of opening the app. New components go into the `Gallery` view of `DesignShellTests.swift`. A screen takes its data as a plain value (`RecoveryCenterState`, `AgentRunsState`, `VerificationState`, `SourceControlState`, which wraps the `VerificationState` of the loaded attempt, `ApprovalInboxState`, `SpecificationsState`, which wraps the `ApprovalInboxState` of the loaded review, `ActivityState`, `SettingsState`, `ExecutionPlanState`, which holds the `ApprovedPlan` values the workspace read) so that it can be rendered with test rows; system controls and scroll views do not draw off screen (use `CheckBox`, `InputField` and `Scrolling` from `Surfaces.swift`).
- The boundary guard rejects the bare word `Process` anywhere in the Swift sources outside `HelperProcess.swift`, in user-facing strings too ("Process group" failed the gate; "process group" passes).
- The snapshot has no `attempt` rows from the real helper: attempts are the `scheduler_attempt` rows and `worktree_admin` rows carry the same identity (`AgentRunsState.attempts(in:)`). A redesigned screen is added to `MainView` beside `RecoveryCenterScreen`, outside the padded group, and to `MainView.built`, and navigates through a closure that sets the shell's screen. `MainView` keeps every screen alive at opacity 0, so `onAppear` fires for all of them at launch: a screen that reads on its own (Activity & Audit, Execution Plan) is told when it is the shown one (`visible`) and reads only then.
- The Swift package keeps one test target. This toolchain runs each test target as its own bundle and the gate reads the last test summary only, so tests in a second target would not be counted.
- The GUI scenarios drive the model through `--ui-script`, not the views; they do not notice a broken layout.
