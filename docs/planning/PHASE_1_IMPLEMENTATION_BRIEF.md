# Jojo — Phase 1 implementation brief

Status: **ready for human scope/ADR review, not approved to implement**. This brief replaces the ambiguous Stage 1 kernel-only interpretation for the next milestone: build the durable architecture foundation and prove parallel scheduling plus safe close/recovery **with fake providers**. It is not a live application-generation milestone. Confirmed requirements and proposed defaults are separated in [ADR drafts](../architecture/ADR-DRAFTS.md); U01–U05 must be resolved before implementation approval is complete.

## Outcome and boundaries

Deliver a minimal SwiftUI review/lifecycle shell connected to a Rust helper, authoritative SQLite state, complete human-authored feature fixtures and revision-bound approvals, typed dependency evaluation, configurable parallel scheduling, independent owned worktrees/attempts/results, local evidence and validated stop/reopen/continuation. Default concurrency one, tests greater than one for mixed Claude/Codex identities and independent repositories. No fundamentally single-agent state or launch loop.

Allowed after explicit Phase 1 approval: local Rust/Swift/test implementation, SQLite migrations, test-only fake executables, temporary disposable local Git repositories and UI fixtures. Research clones and existing `agentic-factory` remain unchanged. This brief does not authorize provider CLI inference, real provider launches/status probes, remote repo creation, push/PR/merge, deployment, live Figma/SCM connections or reading provider credentials. Do not package a provider binary.

Discovery in this phase means persisted questions/answers and human-authored PRD/use-case fixtures, not LLM generation. Architecture options/ADR content is entered/imported and reviewed, not generated by inference. Real CLI adapters, subscription assurance and agent-generated features are subsequent scoped milestones. A fake provider's claimed pass never bypasses independent validation fixtures.

## Shared contracts and deterministic test strategy

Normative design inputs: [core model](../architecture/CORE_STATE_MODEL.md), [parallel scheduler](../architecture/PARALLEL_SCHEDULER.md), [provider contracts](../architecture/PROVIDER_CONTRACTS.md), [shutdown](../architecture/SHUTDOWN_RECOVERY.md). If implementation needs to change an invariant, record a proposed design amendment before silently weakening tests.

Test tools: injected clock/ID sequence; controlled fact store; fake process inspector; event barriers/latches rather than elapsed sleeps; subprocess fixtures that can wait, emit fragmented data, spawn children, ignore signals or die at controlled points; temporary SQLite files and local Git repos; a fake helper for Swift tests. Real OS integration tests use explicit ready/exit handshakes and bounded watchdogs only as failure bounds. They exercise local fake executables, never named `claude`/`codex` discovered through PATH.

All tests run without provider credentials, network, Figma, GitHub, deployment, physical device or model responses. Seeded human approval records are test-only fixtures, not approval of these draft ADR files. Assert durable state/event/claims/results and actual process evidence, not merely snapshots of implementation text or mocked calls matching internal functions.

### P1-01 — Workspace and domain boundaries

**Scope:** minimal Rust domain library and separate helper executable; test target/fake fixture boundary; Swift project boundary without visual design work; choose maintained dependencies/toolchain with recorded provenance. Do not restructure or initialize upstream checkouts. Record accepted implementation ADRs only as explicitly approved by the user, preserving original drafts/history.

**Acceptance:** buildable foundation contains no provider SDK/auth/network/deployment implementation; domain accepts injected clock/IDs; no global current-agent slot; local data root configurable for tests. New code is kept separate from docs/research.

**Deterministic tests T01:** build/typecheck Rust targets; static dependency/launch boundary check rejects forbidden provider/remote integration; run with an empty temporary home/credential-free environment and no network. Do not add meaningless placeholder tests just to raise counts.

### P1-02 — Authoritative writer, idempotency and engine ownership

**Scope:** schema version/migrations for minimum core tables; one writer queue; revision CAS; command receipt deduplication; append-only event sequence; effect/claim transaction primitive; OS singleton lock and engine epochs. No full event-sourcing framework or separate DB service.

**Acceptance:** transition/event/outbox/claim mutations commit atomically; stale revision conflicts; one helper writes the DB; startup admission closed; duplicate ID/different payload rejected. Queries return consistent snapshot/cursor.

**Deterministic tests T02:** two simultaneous commands with same revision yield one winner; duplicate request returns original response; forced failure before commit leaves no partial event/claim; helper B denied while A owns lock; after A dies B starts new epoch with admission closed; migration failure leaves usable prior DB/backup and no workers.

### P1-03 — Artifact, question and PRD/use-case records

**Scope:** immutable version records and content/rendered digests; persisted question/answer provenance; PRD completeness validation; manual import/render of bounded typed content. Minimal schemas include full use-case flows and acceptance/NFR/assumption/blocker fields. Markdown file presence is not completeness.

**Acceptance:** artifact edits create new versions; old versions unchanged; exact reviewed bytes identifiable; missing required fields/placeholders/unanswered blocking questions prevent review readiness. Domain completeness is structural plus human review, not a claim that a validator discovers all product ambiguity.

**Deterministic tests T03:** complete sample passes structural validation; missing alternate/error flow or acceptance ID fails with field path; duplicate IDs, ambiguous JSON keys and oversized/deep input rejected; answer survives restart; rendering round-trip preserves canonical revision/digests. Provenance text retained for any adapted templates.

### P1-04 — Human approvals, stale review and revocation

**Scope:** approve/reject/revoke commands for PRD, ADR bundle and execution plan; exact binding to current artifact/upstream decisions; conservative invalidation; affected-live-run stop intent. Trusted UI channel is the only approval authority; test fixtures explicitly identify fake human origin.

**Acceptance:** all three applicable gates required for development; no agent event or Markdown checkbox can approve; stale UI requests fail; changing a PRD makes downstream approvals inapplicable without deleting history. Revocation outranks cooldown and cannot silently restart work.

**Deterministic tests T04:** stale digest/revision approval conflicts; PRD edit invalidates ADR/plan; cancelled/revoked permission prevents RESERVED→STARTING; fake provider “approved” event has no authority; post-launch revocation requests stop and excludes result applicability; sealed historical result unchanged.

### P1-05 — Graphs, typed predicates and source materialization

**Scope:** explicit nodes/edges for artifact and execution DAGs; versioned closed predicate types; tri-state evaluation with reasons/freshness; immutable plan graph revisions; selected output/source-vector bindings for dependent work. Future SCM/deployment facts represented as fakes only.

**Acceptance:** one evaluator for event/sweep/recovery/prelaunch; all edges AND-combine; missing/unknown/stale cannot satisfy; no PR-open-only edge; isolated nodes supported; dependent base derives from selected predecessor commit/snapshot rather than an unrelated branch tip.

**Deterministic tests T05:** cycle path, self/duplicate/missing reference rejection and diamond ordering; fake opened-PR blocks; failed CI lookup UNKNOWN blocks; expired/wrong-commit/wrong-env deployment blocks; matching receipt unlocks only exact dependent; predecessor branch-tip mismatch prevents materialization; invalidated receipt stops an affected active step.

### P1-06 — Atomic multi-resource admission and fairness

**Scope:** durable capacities/claims/quarantine, one unsealed attempt per step revision, admission gate, reservation/launch-intent ownership, deterministic repo round-robin/priority aging/drain barriers; configuration revisions and cap changes. Async execution separated from writer decisions.

**Acceptance:** entire resource set acquired or none; no partial-hold deadlock; both provider identities schedulable; independent repos can overlap; unknown-live claims count; cap shrink halts admissions without killing; cancellation handled before backoff. Fairness retains original ready order across capacity waits and restart.

**Deterministic tests T06:** cap-one/two/mixed providers; competing admit for one step yields one reservation; saturated repo/provider does not block unrelated job; exclusive waiter drains shared repo holders; three-skipped large request establishes drain barrier; cap shrink/rise and stale config admission; expired heartbeat never releases a live/unknown claim. Test uses fake facts and barriers, not provider inference.

### P1-07 — Local Git and independent worktree ownership

**Scope:** register temporary repos with canonical common-dir identity; owned worktree/branch allocation, short exclusive admin phases and shared execution gates; candidate commit/snapshot collection and safe continuation materialization. Refuse `agentic-factory` and research/upstream paths in test/application fixtures; no remote operations.

**Acceptance:** distinct worktree and output path per attempt; aliases share repository gate; no reset/clean of user work; interrupted work retained; default continuation forks preserved candidate into a new owned worktree. Shared caches/build paths require explicit claims.

**Deterministic tests T07:** two pre-provisioned worktrees same repo with separate edits at cap two; linked aliases collide correctly; independent repos overlap; admin waits for active shared claims; dirty/staged/untracked/modes/symlinks retained or omissions block; traversal/outside-owned-root rejected; no fetch/push/remote-create commands produced.

### P1-08 — Neutral provider DTOs and deterministic fake adapters

**Scope:** LaunchSpec, capability enums, readiness categories and normalized events; independent fake Claude/Codex adapters with synthetic supported/unsupported modes. No custom auth, SDK or invocation of installed official CLIs.

**Acceptance:** attempt/session/turn/process IDs never inferred from “latest”; permission input and product approval distinct; optional capabilities explicit; auth unknown denies Start; fixtures can interleave/fail/wait without shared mutable adapter state.

**Deterministic tests T08:** two fake sessions interleaved without cross-talk; exact-session continuation references; unsupported input/interrupt explicit; unknown auth/key-mode rejects; provider “success” event cannot seal feature or release claims; schema/version mismatch fails before launch. Protocol fixture provenance captured if adapted from upstream tests.

### P1-09 — Process manager and raw stream durability

**Scope:** explicit executable/cwd/env launch of fixture programs, process identity/group/known-descendant registry, issue journal, bounded stdout/stderr spooling/normalization, process exit observations and capability-specific interrupt→terminate mechanism. No inference or arbitrary repository hook execution in fixtures.

**Acceptance:** no spawn inside DB transaction; launch ambiguity retained; output flood cannot block control; offsets reflect flushed bytes; request-stop distinct from observed death; PID-reused process never killed; providers cannot inherit control/DB descriptors.

**Deterministic tests T09:** ready/exit barriers, fragmented UTF-8/NDJSON, malformed/oversized output, stderr flood/backpressure; cancel at reservation/issued/spawn registration barriers; fixture CLI exits with child alive; signal-ignoring/escaped-child identity scenario produces unconfirmed stop; root/child death proof; wrong PID start time no kill; injected write failure closes admission. Real process tests use only temporary test executables.

### P1-10 — Immutable outcomes, independent validation and evidence

**Scope:** classify attempts with ordered stop/completion rules; append-only result and validation receipts; hashes/durable blob references and partial coverage; candidate selection/acceptance separate from invocation success; effect journal with issued-unknown state. Fake remote observations only; no remote mutation adapter.

**Acceptance:** one final result per attempt; process-unknown cannot finalize; success needs terminal/exit/durable candidate evidence; missing terminal after known shutdown is INTERRUPTED, not success. Independent validation binds approved test plan/source and expected test inventory; zero/missing/stale tests fail readiness.

**Deterministic tests T10:** exit-zero/no-terminal with complete durable coverage yields FAILED(protocol_incomplete); lost coverage remains recovery-required until classified; terminal-success/nonzero-exit fails; cancel-before/after finalization follows writer order; concurrent finalizers one winner; attempted result mutation fails; missing blob/truncated log/empty inventory blocks; fake developer cannot change baseline and pass; effect committed-but-ack-lost remains issued-unknown and cannot be replayed. Blob rename/DB reference fault boundaries preserve either valid reference or orphan, never fabricated evidence.

### P1-11 — Reopen inspection and safe continuation

**Scope:** boot paused; inspect old attempts/claims/processes/repositories/effects/logs; quarantine unknowns; recovery resolution records; reviewed continuation plan creates new attempt/worktree with predecessor/session policy. No automatic transparent stream reattachment.

**Acceptance:** unknown/reused-PID/missing-path/stale approval blocks new writer; confirmed-dead work offers validate-output/fresh-context/supported-history/hold choices; no `--last`; stopped attempt/result immutable; unknown side effect not blindly replayed. User manual confirmation alone cannot prove an unknown process absent.

**Deterministic tests T11:** kill helper after reservation/issue/spawn/output/result barriers; reopen sees expected ambiguity and retains claims; process inspector scenarios live/dead/reused/unknown; repo moved/common-dir replaced/HEAD changed/dirty snapshot mismatch; session absent/cwd unsupported gives fresh-context proposal only; continuation new identity and preserved original worktree; completed effect receipt prevents duplicate operation.

### P1-12 — Close-ticket and shutdown coordinator

**Scope:** PrepareClose/CancelClose/ConfirmClose, global layered admission gates, all-worker target sets, parallel stop handling with approved budgets, verified stop/evidence finalization and ShutdownReady/Failure receipts. GUI disconnect starts emergency stop; no background mode.

**Acceptance:** no-active no-confirm close; Cancel sends no signals/restores only close gate; Confirm interrupts all active attempts without permanent task cancel; forced-stop route exposes graceful failure; unknown stop/disk failure cannot acknowledge clean closure. Expired ticket/old epoch rejected.

**Deterministic tests T12:** active count changes while dialog open; reservation/spawn races; two provider trees plus test worker stop; cancelled close continues jobs; success/stop race deterministic; timeout then verified KILL shows escalation; denied/unknown child stop leaves failure and claims; pipe EOF stops admission without user confirmation; queued-only work retained.

### P1-13 — Versioned stdio IPC and snapshot/event replay

**Scope:** helper handshake/epoch, command receipt correlation, consistent snapshot/cursor and bounded event/log queries; shutdown/control priority; protocol errors; disconnection receipts. No Unix socket or reconnect-to-lost-pipe promise.

**Acceptance:** only protocol on stdout; payload/frame limits; UI knows acknowledgement vs completed operation; duplicate ID safe; consistent event sequence across snapshot boundary; mismatch allows diagnostics but no mutation. Existing live helper prevents replacement instance.

**Deterministic tests T13:** fake-helper fragmented frames/oversize/malformed response; dropped response then receipt query returns original operation; event arrives during snapshot query without gap/loss; duplicate/out-of-order event projection; helper crash without ShutdownReady stays unknown; output flood does not delay injected close command indefinitely; child fd inheritance check.

### P1-14 — Minimal native SwiftUI review and lifecycle shell

**Scope:** feature/question/artifact review, approval/rejection with exact displayed bundle; run list/blocked reasons/cancel; close confirmation/progress/failure; interrupted-task recovery choices and evidence paths. AppKit delegate coordinates quit/last window policy while UI remains SwiftUI. No marketing design or native terminal emulator.

**Acceptance:** no DB writes in GUI; approvals use current digest; UI does not call normal termination until ready receipt + helper exit; CancelClose continues; failure stays visible; reopen shows interrupted/unknown jobs without automatic execution. Closing an auxiliary window obeys U02.

**Deterministic tests T14:** Swift model tests against fake helper and focused macOS UI tests for idle quit, pending draft-save failure, active Cancel, confirmed close with progress, graceful timeout/stop failure, duplicate Cmd-Q, last-primary/auxiliary window distinction, stale review rejection and interrupted-work display. Use barrier-driven fake states, not live providers or Maestro.

### P1-15 — Offline feature and parallel execution acceptance

**Scope:** integrate complete fixture PRD/use cases, ADR and plan; synthetic human decisions; two independent temporary repos; fake Claude/Codex developers; separate validator; typed dependency branch; review/evidence UI; close/reopen/continuation scenario. This demonstrates foundation behavior, not AI software quality.

**Acceptance:** end-to-end blocks before all approvals; cap-one serial operation and cap-two overlap both proven; independent worktrees/results; PR-open fixture cannot unlock downstream; validated output can satisfy the exact predicate; shutdown interrupts all active processes; restart offers safe new attempts without altering original records.

**Deterministic tests T15:** orchestrated barriers require both provider fixture processes to reach RUNNING before either completes at cap two; assert no overlap at cap one; revocation mid-run excludes outputs; active-close-cancel leaves processes; confirmed-close/reopen preserves candidate hashes/logs and no automatic dispatch. Execute a same-repo pre-provisioned-worktree case under elevated policy as well.

### P1-16 — Crash, resource and durability campaign

**Scope:** systematic kill/fault points over integrated admission/launch/stop/commit/blob/log protocol; Mac identity/clock/sleep simulations; backup/restore and disk failure; permission boundary tests. This is required foundation safety, not deferred packaging polish.

**Acceptance:** every failure leaves either a valid committed result or explicit interruption/recovery hold; never a false success, unsafe replacement, missing-claim orphan silently ignored or auto-replayed effect. Known-dead candidate evidence remains inspectable after restore. Same-user hostile-code isolation remains explicitly unsupported.

**Deterministic tests T16:** parameterized fault boundary matrix; seeded concurrent command/event schedules; fake reboot/clock jump never frees live ownership; disk-full on stop/result/log flush fails clean close; restored DB/blob integrity; unknown process/repo inspection blocks; cancellation during resource drain; malicious output/forged approval command denied by channel boundary. Real OS SIGKILL test uses disposable helper/fixture process only and verifies cleanup or quarantine, never name-based killing.

### P1-17 — Human readiness packet and provenance review

**Scope:** versioned test evidence with platform/tool/schema/config identifiers, invariant coverage, known limitations, changed-file/provenance ledger and a concrete later live-provider proposal. No new implementation added just to expand this milestone.

**Acceptance:** all T01–T16 required scenarios passed or milestone explicitly blocked; retain evidence for failures/forced stops; no hidden live calls; licenses/notices preserved for any reused content/fixtures; Stage 1 report hashes/research checkouts unchanged. No draft becomes accepted automatically when tests pass.

**Deterministic checks T17:** verify local links, fixture/tool/source digests and manifest completeness; clean upstream `git status` and Stage 1 input hashes; enumerate process-launch paths to ensure only reviewed fixture executables used in Phase 1 suite; review absence of remote/inference adapters. Human review assesses residual risks and approves any next stage separately.
