# Licensing and security

Audit date: 2026-11-14. This is source-based engineering due diligence for personal local use, not a legal opinion or penetration test. Upstream license files were inspected; dependency-wide license/SBOM and binary provenance clearance remain release prerequisites. No credentials were read and no inference was run.

## Official CLI authentication boundaries

Official pages were checked on 2026-11-14; these are live service policies, not immutable commit snapshots. Re-check before prototype provider integration and before any distribution.

**Claude Code:** the [legal page](https://code.claude.com/docs/en/legal-and-compliance) allows an end user to sign into the unmodified binary with their own subscription, including on a hosting platform, and forbids intermediating credentials. The [Help Center update dated October 7, 2026](https://support.claude.com/en/articles/15036540-use-the-claude-agent-sdk-with-your-claude-plan) says plan-signed-in `claude -p` still consumes subscription limits. The [SDK overview](https://platform.claude.com/docs/en/agent-sdk/overview) still warns against third-party products offering Claude.ai login/rate limits. These scopes/texts are not fully harmonized. Our narrow recommendation is personal invocation of the installed, unmodified CLI using its own login; it is **not** permission for an embedded login, credential proxy or redistributed harness. Revisit provider guidance if the project becomes a product. The [programmatic CLI page](https://code.claude.com/docs/en/headless) establishes the subprocess interface.

**Codex:** [authentication documentation](https://developers.openai.com/codex/auth) supports ChatGPT subscription sign-in for local Codex clients. [App-server documentation](https://developers.openai.com/codex/app-server) describes client integration and currently distinguishes permitted local/open-source app-server authentication from commercial/hosted use. Its migration guidance does not imply this personal tool needs to implement its own sign-in product now. Use the existing CLI session and documented interface; do not copy tokens or impersonate an official client. Source confirmation of auth-policy handling: [`codex-rs/app-server/tests/suite/v2/config_requirements_login.rs`](https://github.com/openai/codex/blob/7924f95421a326bb66426a3ce232b72550948470/codex-rs/app-server/tests/suite/v2/config_requirements_login.rs).

The factory should record only provider mode, capability/version, session references and auth status categories. CLI-owned login/refresh/storage stays inside the CLI. A future runtime can report “sign in with the official CLI” on auth failure; it must not fall back to an API key, paid extra usage, a different provider or an undocumented OAuth endpoint. Existing subscriptions are limited, not unlimited inference. Do not infer actual monetary billing from Optio's token-cost estimates. Avoid inference-based authentication probes such as Optio's renewal command.

The no-key/no-paid-call restriction was observed throughout this audit. In the proposed app, do not remove or patch built-in CLI auth functionality; choose the subscription path and decline unsupported configurations. A minimal child environment can omit inherited API-key/provider-routing variables without modifying the CLI. Verify reported auth mode through supported CLI/status interfaces; if uncertain, block rather than guessing. Provider-side extra-usage settings may require user verification; a local wrapper cannot guarantee every billing policy merely by seeing no API key.

### Explicitly excluded credential handling

[`apps/cli/src/local/claude-credentials.ts`](https://github.com/jonwiggins/optio/blob/f5f5b86da3cfa75e240637292a299dc5c6ffc5ba/apps/cli/src/local/claude-credentials.ts) directly reads credentials and may make a model call to renew them. [`apps/api/src/services/local-auth-refresh-service.ts`](https://github.com/jonwiggins/optio/blob/f5f5b86da3cfa75e240637292a299dc5c6ffc5ba/apps/api/src/services/local-auth-refresh-service.ts) coordinates forwarding. These are **DISCARD**, not reusable authentication modules. Do not read CLI Keychain entries, parse auth caches, record bearer tokens, offer a new Claude.ai login, export credentials to workers or route model HTTP requests ourselves.

### Figma is a separate permission boundary

[`src/services/figma.ts`](https://github.com/GLips/Figma-Context-MCP/blob/c083d65c7e002923e7cb98f4e3bdafb105e90f6d/src/services/figma.ts) requires Figma PAT/OAuth headers; [`src/config.ts`](https://github.com/GLips/Figma-Context-MCP/blob/c083d65c7e002923e7cb98f4e3bdafb105e90f6d/src/config.ts) enforces credentials for stdio/fetch modes. [Official desktop MCP setup](https://developers.figma.com/docs/figma-mcp-server/local-server-installation/) requires eligible plan/seat and the desktop application. ## Evidence integrity and independent validation

An evidence manifest should include attempt ID, feature/PRD/ADR/test-plan revisions, every repository HEAD and dirty-diff hash, tool executable/version, command/exit/signal, start/end timestamps, runner identity, device/OS/build identity, deployment/contract references, output hashes, omissions, result and supersession. Store raw artifacts separately from human-readable summaries.

A developer agent cannot change an approved acceptance plan or baseline to make its own run pass. Run verification from a fresh checkout/worktree at the candidate commit, with a separate CLI session/context if an agent review is used. Use the same subscription/provider if necessary; a different model alone is not independence. Trusted deterministic tests and source-bound evidence matter more than model diversity.

In a single-user host, process separation and filesystem permissions do not defend against a malicious same-user agent with unrestricted shell access. The prototype's trust model must be trusted local repositories with scoped CLI permissions and retained human approval. Strong adversarial isolation would require an explicitly approved OS/container/VM boundary compatible with tool auth and macOS UI testing; this audit does not claim worktrees or logical “roles” provide it.

## Recovery and persistence risks

A SQLite state update plus filesystem artifact plus remote effect cannot be one atomic transaction. Write complete blobs to temporary files, fsync/rename appropriately, then commit references; sweep unreferenced blobs later. Store effect intent and outbox records in the same DB transaction as state changes. In-flight unknown outcomes retain their evidence/worktrees and block dependent work.

Use a maintained SQLite build with applicable WAL fixes, a single engine writer and tested backup/restore. The [SQLite WAL documentation](https://www.sqlite.org/wal.html) identifies a WAL-reset fix in 3.51.3 and selected backports; do not blindly use an old system library. The [backup API](https://www.sqlite.org/backup.html) supports consistent live snapshots; copying only an active main DB file is not a backup strategy. Tool versions and packaged library provenance must be verified during implementation.

## Audit exclusions and acceptance before integration

No claim of complete license clearance, CVE absence, sandbox security, crash durability or subscription entitlement is made. Before adopting a component later: resolve selected release/binary licenses, verify provider policy and supported login mode, run focused adapter/recovery tests, confirm evidence coverage, and validate on the actual Mac/simulator. These are concrete integration requirements, not work performed in Stage 1.
