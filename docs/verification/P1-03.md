## 1. Dependency assessment (made before implementation)

Question: should the hand-written SQLite FFI (`sqlite.rs`, 575 lines) and SHA-256
(`digest.rs`) be replaced by maintained crates (`rusqlite`, `sha2`) as part of P1-03?

**No. It should be a separate, explicitly approved refactoring task, and it was not
combined with P1-03.** Reasons:

- It changes a recorded boundary, not an implementation detail: zero external packages,
  offline Cargo, a lockfile with no registry entries, and a guard that names `rusqlite`
  as forbidden. Lifting that needs your approval to fetch and vendor/pin crates and a
  licence/provenance entry, none of which P1-03 authorizes.
- P1-03 does not need it. It adds no FFI surface (no new `unsafe`, no new SQLite
  functions) and uses the existing `sha256_hex` unchanged.
- P1-03 raises the stakes of the digest: `sha256_hex` now identifies reviewed bytes, not
  only request payloads. That is an argument for doing the migration soon — ideally
  before P1-04 binds approvals to these digests — but as its own change with its own
  evidence (same vectors, same on-disk digests, T02/T03 unchanged).
- The migration is contained: `sqlite.rs` and `digest.rs` are the only two files that
  would change behind unchanged crate-internal interfaces.

A strict JSON reader was also hand-written (`json.rs`). A maintained parser would not
remove it entirely: the rejections T03 requires (duplicate keys, depth/size bounds before
allocation, no floats) are not `serde_json` defaults. It can be revisited in the same
refactoring task.

## 2. What was implemented

| Area | Implementation |
|---|---|
| Typed PRD schema v1 (`jojo-domain::prd`) | Title, goal, non-goals, actors, use cases (preconditions, main flow, alternate flows, error flows, postconditions, acceptance IDs), acceptance criteria, NFRs, assumptions, blockers |
| Strict bounded import (`jojo-domain::json`) | ≤ 256 KiB, nesting ≤ 16, duplicate keys refused (compared after unescaping), integers only, no NUL/BOM/unpaired surrogates/trailing content; unknown, missing or mistyped members refused with field path; document-wide unique well-formed IDs; single-line text |
| Canonical form | Fixed member order, no whitespace, one escaping. `import(canonical) == document` and `canonical(import(canonical)) == canonical` |
| Rendering | Deterministic Markdown showing every field, including empty sections |
| Structural validation | Findings with field paths: empty required text/list, placeholder text, unknown actor/acceptance reference, open blocker |
| Artifact versions (`jojo-storage::artifacts`, schema v2) | Artifact = aggregate of kind `artifact`; its revision is the version number. Each version row holds canonical content, rendered bytes, SHA-256 of each, parent revision, creation event, epoch, author and provenance text |
| Questions/answers | Question = aggregate of kind `question` (state `BLOCKING`/`DEFERRED`) plus an immutable row with feature/artifact context and provenance; answers append with an ordinal and human/model provenance |
| Review readiness | Computed for the newest version: structural findings plus blocking questions whose newest answer is missing or not human. Returns the revision and both digests it was computed for |

Reused, not duplicated: revision CAS (`create_aggregate`/`update_aggregate`), events,
command receipts/idempotency, the migration runner and backup, `sha256_hex`, the
`text_enum!` macro, typed IDs and `Revision`.

Not implemented (later tasks): approval/rejection/revocation and invalidation (P1-04),
ADR/plan artifact types and graphs (P1-05), IPC and UI (P1-13/14). There is no helper
command for import: the guard forbids filesystem access in the helper, so "manual import"
is the library API `PreparedPrd::import(bytes)` + `Tx::create_artifact`/`revise_artifact`.

## 3. Invariants

1. **Versions are immutable.** No update or delete API exists; schema triggers refuse
   `UPDATE`/`DELETE` on versions, questions and answers from any connection.
2. **An edit is a new version.** `revise_artifact` is a CAS on the newest revision; a
   stale base conflicts and writes nothing. A revert is a new version with the old
   content digest, not a return to the old row.
3. **A version can only be appended at the aggregate's current revision**, carrying the
   digest the aggregate names, with `parent = revision − 1` and its parent's feature/type
   (trigger and `CHECK`).
4. **Exact reviewed bytes are identifiable.** `rendered_digest` is the plain SHA-256 of
   the stored rendered bytes; `content_digest` of the canonical content. Every read
   re-hashes both and reports `Corrupt` on mismatch.
5. **Only strictly imported content is stored.** `PreparedPrd` can only be built by
   `import`; parsing happens outside the write transaction.
6. **Readiness is computed, never stored**, and is not approval. Markdown presence plays
   no part in it.
7. **Atomicity and idempotency are inherited from P1-02**: a refused import leaves no
   version, event, aggregate or receipt; a replayed command returns its stored response.

## 6. Decisions you may want to overrule

- **Only a human answer settles a blocking question.** A model answer is stored with its
  provenance but the question keeps blocking; a newer model answer after a human one
  makes it block again. Deferring is an explicit, revisioned change.
- **`blockers` in a PRD means open blockers.** Any entry prevents readiness; resolving
  one is a new version without it. There is no "resolved blocker" record in the document.
- **Every use case needs at least one alternate and one error flow**, non-empty
  preconditions/postconditions and at least one acceptance ID. A use case with genuinely
  none must say so in words.
- **Drafts are stored.** Structurally incomplete but well-formed content becomes a
  version and is reported not ready. Duplicate IDs, unknown members and multi-line text
  are refused at import instead.
- **Identical re-import is refused**, not treated as a no-op success.
- **Question scope**: a blocking question blocks its own artifact, or every artifact of
  its feature when it names none.

## 7. Limitations

- Placeholder detection is a short word list (`TODO`, `TBD`, `TBC`, `FIXME`,
  `PLACEHOLDER`, `???`, `NEEDS CLARIFICATION`, `LOREM IPSUM`). Passing validation means
  structurally reviewable, not unambiguous or correct.
- Only the PRD artifact type exists. The schema's `artifact_type` check must be widened
  by a migration when ADR/plan types arrive.
- No template text was adapted, so the "provenance retained for adapted templates" clause
  is exercised with a synthetic notice, proving storage and retention only.
- Text is compared byte-for-byte; no Unicode normalization. Visually identical strings
  in different normal forms are different content.
- Digest integrity depends on the hand-written SHA-256 (section 1) and, as before, does
  not defend against a same-user process that rewrites both bytes and digest.
- `verification/p1-02-result.json` fingerprints no longer match the files listed in
  section 4, by the same precedent as P1-01's after P1-02.
