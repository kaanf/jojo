## Scheduler architecture and resource model

The existing single SQLite writer serializes decisions, not invocation lifetimes. `Tx::queue_step` explicitly queues a reviewed step for RUN after current approval/dependency/source validation. `Tx::schedule` accepts a configuration revision and injected attempt IDs, fills capacity in deterministic repository passes, and returns admitted/waiting decisions. It performs no process, filesystem, Git or network operations. Concurrent callers can compete through the writer without admitting a step twice.

Execution-plan schema **2** extends the canonical reviewed plan with one resource envelope per step: provider identity, repository, shared/exclusive repository mode, bounded base priority and additional named resource quantities. Mandatory global, provider and repository claims are derived, so a caller cannot omit them or override them through additional resources. Provider identities are Claude Code and Codex; neither binary is inspected or executed. All resource declarations participate in the existing plan digest and human review bundle. Schema **1** plan bytes remain readable and canonically identical; they require a new reviewed resource-bearing revision before scheduler admission. Predicate and observation schemas remain **1**.

Migration **5** appends immutable configuration/capacity snapshots, queue state, cursor, logical barriers, reservation identities, claim quantities, heartbeat observations and provider cooldown observations. Shipped global/provider/default repository capacities are **1**; zero explicitly pauses a resource class. Repository overrides and named capacities are configurable. A repository key combines its quantitative slot limit and shared/exclusive activity exclusion. Named resources may reserve multiple units or require exclusivity. Missing named capacity blocks admission. Repository identity must match the reviewed source identity.

Every resource uses the P1-02 durable claim primitive, associated with a unique attempt aggregate and owning engine epoch. Claim quantities supplement the existing claim record. All non-released claims count, including quarantined and old-epoch claims. Heartbeats are append-only hints: neither their expiry nor clock advancement releases resources. Configuration decreases preserve incumbents and block new work until the complete requested set fits; increases affect the next scan. No preemption occurs.

## Transaction boundaries and recovery

One admission transaction checks current approvals and plan revision, exact step/source bindings, the P1-05 predicate evaluator, current configuration, intent/control state, cooldowns, engine gate, unsealed attempts, claims, quarantine and complete capacities. It writes the RESERVED attempt, frozen dependency inputs, full resource claim set, event, cursor/barrier changes and unique NOT_ISSUED launch intent together with the command receipt. Failure rolls everything back, including earlier admissions in that same command. No partial resource holds or asynchronous execution occur inside the transaction.

Configuration changes use expected-revision CAS. Step controls also use revision CAS, and CANCEL cannot be reversed for that step revision. SQL constraints enforce one unsealed scheduler attempt, plus a dependency-input trigger covering legacy typed-plan reservations. Command receipts, unique attempt IDs, immutable queue identity and epoch fencing prevent duplicate/stale admission. Original ready timestamp and event sequence cannot be rewritten or deleted.

Cancellation/revocation acts before cooldown. A current-epoch reservation proven NOT_ISSUED can seal NOT_STARTED, persist stop intent and release its complete claim set with NEVER_ISSUED evidence. Its queue becomes HOLD unless already CANCEL, so settlement does not create an automatic retry. The retained outbox intent is invalidated by the reservation/stop tombstone; a SQL issue guard refuses advancing a sealed, stopped, gated or stale scheduler intent. The legacy start API refuses scheduler-owned reservations. A future dispatcher must implement final capability/source/dependency validation and its issue/process boundary; no dispatcher is implemented here.

Issued-unknown attempts and reservations owned by prior epochs cannot use pre-issue settlement. Restart retains queue state, cursor, configuration, skips/barriers and launch identities; existing boot behavior closes admission and quarantines active claims. Reopening does not dispatch or replace anything. The test-only controlled recovery opening of the gate cannot free quarantined occupancy. Full process inspection and recovery resolution remain later work.

## Fairness

Canonical repository-ID queues use a persisted round-robin cursor. Each pass admits at most one job per repository, then repeats to fill capacity. Within a repository, order is effective priority, original ready sequence and step ID. Base priorities are 0–3; eligible monotonic waiting adds one level per ten minutes, capped at three. Capacity waits and scans retain age/order. Control/cooldown intervals do not fabricate age, and incomparable clock epochs cannot age jobs using a wall-clock jump.

Resource-infeasible candidates are skipped with a decision reason; the scan continues within the repository and across other repositories. Provider cooldowns are persisted and affect only that provider. Uncertain cooldown clock scope requires a fresh observation or explicit clear. Cancellation still acts immediately.

An exclusive repository waiter immediately prevents new shared admissions to its repository, including older shared jobs still waiting in the queue. Existing shared holders drain normally; unrelated repositories continue. An older eligible request earns a starvation skip only when a younger request actually obtains a contested resource while the older complete request cannot fit. Polling alone earns no skips. Three such admissions establish a durable logical drain barrier on the contested keys. Barriers never acquire physical resources partially; unrelated keys remain usable. Conflicting barriers favor original ready sequence and step ID, and clear on admission or ineligibility. Tests prove eventual service after incumbents drain, including two conflicting barriers.

## Limitations and architecture compatibility

This is admission/reservation logic, not provider execution, worktree provisioning, process supervision, IPC or automatic recovery. Canonical Git common-directory identity and inspected sources are controlled inputs until P1-07. Multiple independently scheduled repositories and same-repository reservations are supported, but a single admission envelope currently requires one source repository; multi-repository source envelopes fail closed. Material queue/plan rebinding requires a new reviewed step revision, preserving the original queue identity. There is no implicit provider substitution, preemption or retry loop.

Fairness assumes finite incumbents or explicit resolution of hung/unknown work; no claim of starvation freedom under unbounded arrivals is made. Issued/unknown work cannot be settled through this scheduler. Actual dispatcher issue semantics, independent output/worktree path bindings, process-death evidence and full recovery remain their assigned later tasks.

No architecture invariant was revised. Plan schema 2 is an explicit versioned representation of the existing requirement that process-producing steps declare their resources; it does not broaden permissions or silently upgrade prior approvals. Multi-repository execution is a fail-closed implementation limit, not a proposed weakening of atomic acquisition. No P1-07 code, provider authentication, live CLI invocation, network operation, deployment or generic distributed/plugin framework was added. No dependencies or licensing notices changed; new fixtures are original.
