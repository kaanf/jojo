## 1. What was implemented

A new crate, `jojo-storage`, and a small helper command that uses it.

| Area | Implementation |
|---|---|
| Schema and migrations | `PRAGMA user_version` as schema version; ordered plan; each step and its version bump in one transaction; verified backup before upgrading an existing database |
| Single writer | One writer thread drains a command queue; every command is one `BEGIN IMMEDIATE … COMMIT` |
| Compare-and-swap | Integer revision per aggregate; the comparison is the `WHERE` clause of the `UPDATE` |
| Idempotency | Durable receipts keyed by command ID, with a SHA-256 request digest and the stored response |
| Events | Append-only, gapless `AUTOINCREMENT` sequence; each event names its epoch, causing command and aggregate revision |
| Claims and outbox | Transaction primitives only: shared/exclusive claims, `NOT_ISSUED → ISSUED_UNKNOWN → CONFIRMED/REJECTED` effects |
| Ownership | Exclusive `flock` on a sidecar lock file, held for the helper's lifetime |
| Engine epochs | New epoch persisted at every start, admission closed, previous session sealed, old claims quarantined |
| Fencing | Every write transaction re-checks, under the write lock, that its epoch is still the newest running session |
| Snapshots | Query-only connections; one read transaction yields projections plus the event cursor they match |
| Helper | `jojo-helper --engine-probe`: own the database until stdin closes, then record a clean shutdown |

Not implemented (later tasks): scheduler, fairness, capacities, approvals, artifacts,
attempt lifecycle, process launch, IPC protocol, recovery inspection, GUI lifecycle.
Nothing in P1-02 opens admission by itself.

## 3. Database schema and migration design

Schema version 1 (`crates/jojo-storage/src/schema.rs`), all tables `STRICT`:

| Table | Purpose | Rules enforced by the schema itself |
|---|---|---|
| `engine_sessions` | One row per engine epoch: admission gate, shutdown marker | Must start as the next epoch, `RUNNING`, admission `CLOSED`, with no other running session; sealed rows immutable; no delete |
| `aggregates` | Revisioned mutable state `(kind, id, revision, state)` | Created at revision 1; every update advances by exactly one; no delete |
| `commands` | Receipts: digest, response, event cursor, epoch | No update, no delete |
| `events` | Global ordered facts | No update, no delete; deferred foreign key to `commands`, so no event can commit without its receipt |
| `resource_claims` | Shared/exclusive claims with holder and epoch | Conflicting live claim refused; only `ACTIVE → QUARANTINED → RELEASED`; release needs a recorded basis; **no expiry column** |
| `outbox` | Effect intents with payload digest and issue state | Starts `NOT_ISSUED`; only forward transitions; operation immutable; no delete |

Migration rules:

- The storage crate owns the production plan; steps are appended, never edited.
- A file is accepted only if it is empty or carries Jojo's `application_id`; this check
  runs before anything persistent (even the journal mode) is changed.
- A database newer than the helper is refused untouched (`SchemaTooNew`).
- Before upgrading an existing database, `VACUUM INTO` writes a copy next to it; the copy
  is fsynced, reopened and passes `integrity_check`. Backups are never overwritten or deleted.
- A failing step rolls back completely. The database stays at the last whole version, the
  error names the backup, no epoch is created and no writer starts.

Connection settings: WAL, `synchronous=FULL`, `fullfsync=ON`, `checkpoint_fullfsync=ON`,
`foreign_keys=ON` (read back and required), 5 s busy timeout. Runtime library: system
SQLite 3.54.0; 3.37 is the minimum accepted.

## 4. Transaction and concurrency invariants

One command = one transaction, in this order: take the write lock → epoch fence → receipt
lookup → handler mutations → receipt insert → commit.

1. **The database decides, not memory.** The queue only avoids lock contention. The same
   races are tested over two raw connections with no queue and no ownership lock.
2. **CAS.** Two commands with the same expected revision cannot both succeed; the loser
   gets `RevisionConflict` with the actual revision and leaves nothing behind.
3. **Idempotency.** Same ID and request → stored receipt, handler not run. Same ID,
   different kind or payload → `CommandIdConflict`. The epoch is a fence, not part of the
   digest, so a retry after a restart still replays.
4. **Atomicity.** A handler error, SQLite constraint error, injected fault, panic or
   process kill before commit leaves no state, event, claim, outbox entry or receipt.
5. **Rejected commands keep no receipt**, so the same ID can be retried.
6. **Events are honest and gapless.** An event must carry the aggregate's current
   revision; rolled-back transactions consume no sequence numbers.
7. **Fail closed.** A failed commit, failed rollback, handler panic or fence violation
   stops the writer permanently; later commands return `WriterStopped`.
8. **No single-agent assumption.** Aggregates, claims and effects are keyed by arbitrary
   identities; sixteen attempts for two provider identities commit concurrently in tests.

## 5. Singleton ownership mechanism

- The owner holds `flock(LOCK_EX|LOCK_NB)` (`std::fs::File::try_lock`) on
  `<database>.owner-lock`. The kernel releases it when the process dies, including SIGKILL.
- A second helper fails immediately with `OwnershipHeld` (helper exit status 3) and writes
  nothing. It never waits and never infers death from time.
- The database path is canonicalized, so symlink aliases share one lock.
- After locking, the lock file's inode is compared with the path to catch replacement
  during acquisition.
- The lock file holds `pid=… epoch=…` for display only.
- Second line of defence: if the lock is bypassed (lock file deleted while held), the new
  helper's epoch makes the old one stale, and the old one's next write is rejected and
  stops it.

## 6. Crash and recovery behaviour

Guaranteed, and tested:

| Event | Result |
|---|---|
| Helper killed between commands | Next start: new epoch, previous session marked `UNCLEAN`, admission `CLOSED` |
| Helper killed inside a transaction | That command leaves no trace; earlier commands intact; event sequence gapless |
| Duplicate command after restart | Original receipt (original epoch) returned; effects not repeated |
| Previous owner had opened admission | Not inherited; every epoch starts closed |
| Previous owner held claims | Become `QUARANTINED` and keep blocking; released only by an explicit release with a recorded basis. A ten-year clock jump frees nothing |
| Clean shutdown with live claims | Refused; the session stays unclean |
| Late callback from an old epoch | `StaleEpoch`, no change |
| Migration failure | Prior version usable, verified backup present, no epoch, no writer |

Not guaranteed, by design:

- **No atomicity with the outside world.** A committed claim or outbox row is an intent.
  Process launches and filesystem writes are separate from the SQLite commit; the
  `ISSUED_UNKNOWN` state exists to record that gap.
- **A released lock proves only that the helper died.** It says nothing about processes
  the helper launched; that is why claims are quarantined rather than released.
- **Epoch fencing protects database writes only**, not an old child's OS side effects.
- **A lost reply is ambiguous to the caller.** After a crash or a commit error the caller
  must look the command up by ID (`Reader::receipt`) or resend it.
- **Durability is bounded by the hardware.** `F_FULLFSYNC` is requested; storage that lies
  about flushes, or media corruption, is outside what this code can detect or repair.

## 10. Deviations from accepted contracts and from P1-01

No accepted invariant in the normative documents was weakened. Deviations from the P1-01
implementation boundary, each needed to do P1-02 at all:

1. **`unsafe` FFI to the system SQLite.** P1-01 forbade `unsafe` workspace-wide and had no
   external packages. A maintained wrapper (rusqlite, suggested in
   `PROPOSED_ARCHITECTURE.md`) would have required downloading third-party crates, which
   the offline/zero-dependency regime of P1-01 excludes and which nobody authorized. So
   SQLite is bound by hand in one 575-line module. The workspace default stays `forbid`;
   only `jojo-storage` uses `deny` with one opt-in module, and Clippy requires a SAFETY
   note on every unsafe block. **This is the decision most worth your review**: switching
   to rusqlite later is contained to `sqlite.rs`, but needs your approval to fetch crates.
2. **Hand-written SHA-256** for request digests, for the same reason; checked against the
   FIPS 180-4 vectors.
3. **Guard amended.** Filesystem access is allowed in `jojo-storage`; child processes only
   in integration tests and only to launch the test binary or `jojo-helper`; ambient clock
   and environment are now also banned in storage production code.
4. **Helper gained a holding command** (`--engine-probe`). It is not a daemon and not the
   IPC protocol: it exits when stdin closes and ignores input.
5. **`verify_p1_01.py`** no longer writes `p1-01-result.json`; run directly it writes
   `p1-01-regression-result.json`.

Interpretations worth knowing:

- "One writer queue" is a thread and channel, not an async runtime.
- The outbox follows the contract's diagram literally; there is no `NOT_ISSUED → REJECTED`
  edge yet. Cancelling an unissued effect needs a decision in P1-06/P1-10.
- Aggregates are a generic `(kind, id, revision, state)` table; later tasks add typed
  tables beside it.
- `Tx::set_admission` exists because the gate is durable state; the policy for opening it
  belongs to P1-11/P1-12.

## 11. Remaining limitations

- A hard link to the database in another directory gets a different lock file. The epoch
  fence still prevents two canonical writers, but SQLite itself warns against this layout.
- The lock coordinates Jojo helpers only; another program can still write the file.
- The database file is created with default permissions inside the 0700 data root.
- Snapshot queries return whole tables; bounded/paginated queries belong to P1-13.
- No statement cache and no performance tuning; throughput was not measured.
- No backup/restore command beyond the pre-migration copy; no retention policy.
- Disk-full and I/O-error paths are handled by rollback and writer stop, but are exercised
  only through injected faults, not a real full disk.
- The production `SystemClock` exists only in the helper probe; production ID generation
  is still absent.
- macOS only: the binding links the system `libsqlite3`, and the tests assume `flock`.
