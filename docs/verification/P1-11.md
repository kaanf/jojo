## Implementation

**Paused reopen (`Tx::set_admission`).** A reopened database (any earlier engine session) can open admission only after this epoch recorded a recovery start. The first epoch of a new database has nothing to recover and is exempt.

**Read-only inspection (`jojo-storage::recovery::inspect_recovery`).** Subjects are earlier-epoch scheduler attempts that are unsealed, still hold live claims, or are sealed non-success attempts that are still the latest of their step and have no continuation plan. For each subject it derives, from durable records only:

- launch stage: not issued, issued without a recorded identity, spawned, concluded, sealed
- recorded process identities, re-inspected through an injected `ProcessInspector`. The real one (`OsProcessInspector`) takes one snapshot of the explicit `ps` and checks the boot. Each identity is live, absent, reused or unknown. A recorded process group with any live member is unknown, never absent.
- worktree and repository identity (root, common dir, ownership marker, branch). If a candidate was recorded before the crash, a double capture must reproduce its exact digest and HEAD.
- stale PRD/ADR/plan approvals and ISSUED_UNKNOWN effects
- raw-log coverage: spool length versus durable checkpoint; trailing bytes are reported as not evidence
- session continuity: exactly one recorded `SessionIdentified`, round-trip parsed, and declared support for explicit sessions, exact continuation and continuation in a new cwd. Several sessions are never resolved to the "latest".

It signals nothing, adopts nothing and writes nothing.

**Pure assessment (`jojo-domain::recovery::assess`).** Any of the following blocks every choice except Hold:

- a live, reused, unknown or unrecorded process identity
- a missing or changed worktree
- a stale approval
- an effect whose outcome is unknown

There is no input for a human "assume stopped", so a confirmation cannot replace OS evidence. Unblocked work is offered: validate output (if a candidate exists), continue with history (exact session only), continue in fresh context, and hold.

**Writer commands.** Each one re-derives the subject's durable facts digest and refuses a stale inspection.

- `start_after_recovery` records the reviewed inspection and opens admission. Blocked subjects keep their QUARANTINED claims, so they still block conflicting writers. A new worktree in the same repository waits.
- `resolve_recovery` appends a resolution. Hold changes nothing else. An unblocked non-Hold choice behaves as follows:
  - Sealed subject: releases its remaining claims as `RECOVERY_RESOLVED`.
  - Never-issued reservation: retires it as NOT_STARTED.
  - Spawned or concluded subject: writes an absence proof. P1-10 settlement then runs for the earlier-epoch attempt.
- `record_continuation_plan` requires all of the following:
  - a sealed non-success predecessor and an unblocked continue resolution matching the session policy
  - current approvals
  - an exact list of reconciled effects, none still unknown
  - for history, the one recorded exact session
  - a new successor identity

  It records the predecessor result's candidate and source base, and the plan digest.

**Settlement of recovered attempts (`outcomes`, `worktrees`, `scheduler`).** Supervised TREE_ABSENT or NOT_SPAWNED stays authoritative. A crash during settlement therefore still yields the real P1-10 classification, including success. Only when supervision never concluded does a current-epoch proof select the new `RecoveredAbsent` conclusion, which is classified as follows:

- INTERRUPTED(`helper_lost_recovered`) by default
- CANCELLED if a task cancel preceded the crash
- FAILED if a supervisor stop preceded the crash
- never SUCCEEDED

Every gap is kept as an uncertainty. Candidate capture and changed-path inspection accept an earlier-epoch worktree only with such a proof. Effects never use the relaxation.

**Continuation binding.** A successor worktree with a predecessor binds for execution only if a plan names both, for the same step revision. Its materialized snapshot and base must equal the plan's candidate and base. `issue_process_launch` admits `LaunchSpec.continuation` only for an exact-history plan with the same session, predecessor, previous cwd and plan digest. It refuses continuation without a plan, and refuses a missing continuation when the plan requires one. This closes a P1-09 gap, where an arbitrary continuation reference was not checked.

**Schema version 9** adds `recovery_starts`, `recovery_resolutions`, `recovery_absence_proofs` and `continuation_plans`, each with update/delete triggers. Insert guards:

- A proof needs an unblocked non-Hold resolution in the same epoch, for an attempt reserved in an earlier epoch.
- A plan needs an unblocked continue resolution, the predecessor's sealed non-success candidate and a new successor.
- `attempt_result_proof` is replaced so that a proof supports only non-success results. Success still requires supervised TREE_ABSENT, a candidate, both logs and no unknown effect.

Earlier migrations are unchanged. Latest-schema assertions moved from 8 to 9, as previous milestones did. T06 reopen fixtures now open admission through a real inspection and start.

T11 tests cover the following:

- **Kill-at-barrier reopen.** A helper killed after reservation, issue, spawn, output or result reopens with the expected ambiguity. Claims stay QUARANTINED. A sealed success is unchanged and needs no decision.
- **Process inspection.** Real live, different-boot absent, reused-PID and unknown-start identities. A failed inspector on the same records is never treated as absence.
- **Who can unblock.** A trusted-UI "I am sure it stopped" cannot unblock. Hold never signals the live orphan. Only its observed exit makes it resolvable.
- **Worktree drift.** A moved worktree, a replaced common dir, a HEAD changed after the candidate and a dirty-snapshot mismatch each block.
- **Crash during settlement.** An unchanged worktree recovers its real SUCCEEDED result, and the recovered candidate passes independent validation.
- **Session policy.** An absent session, a missing capability profile, unknown history support or unsupported cwd change offers fresh context only. Full support adds continue-with-history.
- **Stale approval** blocks and keeps the quarantine.
- **Stale inspection.** Start and resolve refuse an inspection after its facts changed. Every later reopen needs its own start.
- **No unplanned continuation.** A fresh attempt cannot claim provider continuation without a plan.
- **End-to-end continuation.** An issued effect whose acknowledgement was lost blocks until an exact fake observation. The confirmed-close attempt then seals INTERRUPTED. Plans with missing effects, a different session or the wrong policy, and a duplicate plan, are refused. The successor gets a new owned worktree containing the predecessor's partial work and launches only with the exact reviewed continuation. It cannot journal the predecessor's committed effect again. The original result and worktree are unchanged.
- **SQL guards.** Raw SQL refuses unbacked proofs, success from recovery, invalid plans and every update/delete.

## Limits and next gate

- Helper death is simulated by dropping the engine without a clean shutdown at each durable barrier. The database then holds exactly what a dead helper committed. OS-level helper SIGKILL remains covered by T02, and the integrated kill matrix belongs to P1-16.
- **Design note (stricter than the draft):** the shutdown/recovery draft says a matching live orphan "is stopped and inspected before continuation". P1-09 forbids signalling a PID without a retained lifetime handle, so P1-11 quarantines it instead and requires OS evidence of exit. P1-12 or a later approved mechanism may add a supervised stop route.
- A launch issued without a recorded identity stays blocked, because no identity exists to prove absence. A reused PID blocks as specified until a later inspection finds the identity absent. Descendants that escaped into another group or session without being recorded are invisible to group inspection.
- Validate-output yields a passed receipt for a recovered candidate. Acceptance still requires a SUCCEEDED invocation, so an interrupted candidate is used through continuation.
- Continuation is limited to the same step revision and repository. Detecting materially changed remaining work that needs new plan approval is not automatic.
- Immutability is policy plus SQL triggers and digests, not protection against a hostile same-user process.
