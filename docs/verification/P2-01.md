### Golden argument vector

```
<executable> exec --json --color never --sandbox workspace-write --ephemeral
             --ignore-user-config --ignore-rules -C <owned worktree>     (prompt on stdin)
```

No function, field or parameter can add to it. The 26 excluded options and subcommands (`PROHIBITED_ARGUMENTS`: sandbox and hook-trust bypass, `--approve-for-me`, `--trust`, `--worktree`, `--add-dir`, `--oss`, `--local-provider`, `--enable`/`--disable`, `-c`/`--config`, `--last`, `--skip-git-repo-check`, `--full-auto`, model and profile selection, API-key and access-token login, `danger-full-access`, `resume`, `fork`, `login`, `doctor`) are tested at every insertion and replacement position.

### Executable validation and fingerprint

The configured path must be absolute and fully resolved (equal to its own canonical form), not a symbolic link, a regular file, executable, not set-id, not writable by group or others, at most 1 GiB, and begin with a Mach-O or universal-binary magic number. A `#!` launcher is refused without being run. The file is hashed once; the digest must equal the approved one.

The fingerprint binds `provider`, `executable`, `version` (`codex-cli 0.169.0`, the only release the profile accepts), `schema`, `parser`, and `configuration = jojo.codex.exec/1;sha256=<digest>`. A package update changes the bytes and invalidates the fingerprint.

### Launch environment

The child receives exactly one variable, `CODEX_HOME`, set to the configured path. The spec's allowlist must be exactly `[CODEX_HOME]`. The home must be an existing, fully resolved, non-world-writable directory that does not overlap the worktree, the repository's common directory or the output directory, lexically or after resolution. Jojo checks only the directory's own metadata: it never lists, opens or hashes anything inside it. The runner clears the inherited environment, as before.

### Other profile rules

One fresh developer run: a continuation is `UnsupportedContinuation`; a validator role, a tool allowlist or any filesystem root other than the worktree is `UnsupportedPermission`; config references are `InvalidSpec`. Sign-in mode is a human attestation in the adapter configuration and is never inspected; anything other than `NativeSubscription` is `AuthenticationDenied`.

### Parser behaviour

Modelled records: `thread.started`, `turn.started`, `turn.completed`, `turn.failed`, `item.started`/`item.updated`/`item.completed` for `agent_message`, `reasoning`, `todo_list`, `command_execution`, `file_change` and `error` items, and top-level `error`.

Each of these latches a protocol failure, after which no success can be normalized and the runner requests a stop: a record that is not JSON, not UTF-8, not an object, too deep, over the frame limit or unterminated; an unknown record type; an unknown item type; an `mcp_tool_call` or `web_search` item; a second turn; an item outside an open turn; a missing or over-long identifier; any record after the terminal record.

`turn.completed` is success only with exactly the documented keys, numeric token counts and no earlier error record; otherwise the terminal status is `Unknown`. `turn.failed` is `Error`. Exit status never produces a terminal record. Violation texts are fixed strings; provider bytes stay in the raw spool.

### Capability record

`unverified_capabilities()` records all eleven capabilities as `UNKNOWN`, with evidence "`--version` and `--help` text only; never executed by Jojo". Consequently the stop plan for this adapter is signal-only (TERM, then KILL).

## Security constraints preserved

- No new process-launch site. The only provider launch remains `Command::new(&launch.executable)` in `process.rs`, with a cleared environment and its own process group.
- Agent tool network permission remains false; a spec that sets it is rejected for every profile. No inference-network permission exists in the code.
- No credential, Keychain or `auth.json` access; the boundary guard now refuses those names, install locations and any provider variable other than `CODEX_HOME` in production source.
- No ambient environment or clock access in domain or storage production code (existing guard, unchanged).
- Jojo-owned worktrees, approval bindings, the issue journal, the "one launch per attempt" rule and process supervision are untouched.
- No dependency was added; `Cargo.lock` is unchanged.

## Known limitations and remaining uncertainties

1. **The real stream was never observed.** The parser models documented shapes. If release 0.169.0 emits a record kind, item type or completion field that is not modelled, the run fails closed with complete raw evidence rather than succeeding. That may make the first live attempt end as "protocol failure"; it cannot make it end as a false success.
2. **The version is attested, not measured.** Jojo does not run `--version`. The human records the version for the file whose digest they approve; the digest is what is enforced.
3. **Check-to-use window.** The executable is hashed immediately before the issue journal entry and then launched by path. A same-user process could replace it in between. Closing that window needs launch by file descriptor, which the current safe-Rust process surface does not offer.
4. **Whether `CODEX_HOME` alone is sufficient** for a signed-in 0.169.0 to start (for example, whether it also needs `HOME` or a Keychain session) is unknown. The amendment permits only `CODEX_HOME`; anything more needs a new human decision.
5. **Codex-side behaviour is unverified:** whether hooks, plugins or MCP servers load under `--ignore-user-config`; what the `workspace-write` sandbox allows outside the worktree and whether it blocks the worktree's Git common directory; approval behaviour in `exec`; the real process tree. Scope remains enforced after the run by the existing repository-derived checks, not prevented.
6. **Stderr truncation is recorded, not fatal, at this layer.** A capped stderr produces a `STREAM_TRUNCATED` observation; how settlement treats it is existing P1-10 behaviour and was not changed.
7. **A caller that bypasses the adapter** and names the synthetic Codex parser with an arbitrary executable is constrained only by the Phase 1 rules, as before. No production caller of `run_launch` exists yet; P2-02 must route Codex launches through `CodexAdapter` only.
8. **Provider inference network permission is not modelled.** It is deliberately absent until a live attempt is authorized.
9. **Set-id refusal is not exercised inside the gate.** The OS sandbox the gate runs under silently drops set-id bits on `chmod`, so the two set-id cases are skipped there (they are asserted when the suite runs outside the sandbox, as in `verification/p2-01-dev/storage-focused-3.log`). The other mode cases run in both.
10. macOS only: the native-executable check accepts Mach-O and universal binaries.
