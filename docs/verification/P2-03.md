### How a validation runs

1. `Validate` names the attempt and the sealed candidate digest. It is refused before anything runs for a stale digest, a decided candidate, an active run, stale or revoked approvals, or an approved plan without a command.
2. The runner reads the approved plan the attempt is bound to and derives changed paths from the repository. If a path is out of scope or baseline, the command is **not started** and the receipt fails.
3. Otherwise it creates `<data root>/validation/<run>/`, clones the registered repository there (objects copied, no hooks or templates), checks out the candidate commit, applies the sealed packet (reopened against its digest) and requires the result to capture to exactly that packet.
4. It runs exactly the approved argument vector there through the P1-09 supervised runner, under `sandbox-exec` with the network denied, with a four-variable environment, a 10-minute and 8 MiB budget and TERM-then-KILL stop, and waits for the whole process tree to be gone.
5. It re-checks that the retained worktree still reproduces the sealed digest, stores the report as evidence and records the receipt and the end of the run in one transaction.

The verdict is the observed exit status. Provider output is never read. A run that cannot produce a verdict records none.

### States

`NOT RUN` (never requested), `UNKNOWN` (requested, no verdict: running, interrupted, or impossible to perform), `PASS`, `FAIL`. The GUI maps any unrecognized state to `UNKNOWN`, shows the provider's own terminal status separately as the provider's statement, and offers Accept only for a passing receipt of exactly the displayed candidate. The helper re-checks all of it.

## Deviations and limitations

1. **The protocol minor stays 1.** The P2-03 commands are additive under 1.1. P2-02 regression tests pin minor 2 as "a later minor"; changing them was avoided.
2. **Existing test files gained one line each** (`command: vec![]` in four `StepValidation` literals). No assertion changed.
3. **No database migration.** Runs and rejections are append-only events (`ValidationRequested`, `ValidationEnded`, `CandidateRejected`); exclusivity of accept and reject is enforced in the writer transaction, not by a trigger.
4. **One command, one verdict.** A plan step with a command has exactly one inventory entry, and the receipt reports the command's exit status under that name. Per-test results are not parsed.
5. **The validator sandbox denies the network only.** The command runs with the user's file permissions, so candidate code executed by it could write outside the validation directory. A stricter profile cannot be nested inside the gate's own sandbox. The runner detects a changed worktree or packet afterwards and records no pass, but it does not prevent the write.
6. **Validation directories are kept** under `<data root>/validation/`; nothing prunes them.
7. **The budget is fixed in code** (10 minutes, 8 MiB per stream), not part of the approved plan.
8. **The GUI takes the attempt identity typed by the human** and shows at most 64 log records and 256 KiB of diff.
9. **Acceptance records a decision only.** Nothing is merged, pushed or published; that remains a later, separately authorized step.
10. The real-helper end-to-end step runs outside the OS network sandbox. It is offline by construction, but that is not enforced by the OS for that step.
11. P2-02 limitations 3 and 4 remain, as assessed above. All P2-01 uncertainties about the real Codex CLI remain.
