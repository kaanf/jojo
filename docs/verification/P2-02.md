## Crash-test flake (investigated first)

`a_helper_killed_inside_a_transaction_leaves_only_whole_committed_commands` failed once in the P2-01 final gate with "the child died by SIGKILL, not by exiting" (`signal()` was `None`).

**Cause: a test synchronization race, resting on a wrong assumption about process exit.** It is not a production defect.

- The fixture child prints READY, then blocks reading stdin and calls `exit(86)` on end-of-file ("the parent died").
- The test's `kill()` called `Child::kill()` and then `Child::wait()`. `wait()` closes the child's stdin before reaping.
- On macOS a posted SIGKILL does not stop another thread of the target from running first. The child's reader thread can see the EOF and exit with 86 before the signal takes effect. The parent then observes a normal exit.

Evidence:

| Experiment | Result |
|---|---|
| Minimal C child (reader thread exits 86 on EOF), parent sends SIGKILL then closes stdin, 8 × 1,500 runs in parallel | exit 86 in 1,253 of 12,000 (about 10%) |
| Same, stdin kept open until the child is reaped | SIGKILL in 12,000 of 12,000 |
| The real test binary, 8 × 60 runs in parallel, before the fix | 5 failures in 480 |
| The real test binary (both tests), 8 × 150 runs in parallel, after the fix | 0 failures in 1,200 (`verification/p2-02-dev/flake-stress-after-fix.txt`) |

Fix: the test now takes the child's stdin handle, kills, reaps, and only then drops the handle, so SIGKILL is the only way the child can die. The assertion (`signal() == Some(9)`) is unchanged, no sleep was added and no test was removed. The same latent pattern existed in two helper tests that kill a real helper holding a piped stdin (`t02_helper_ownership.rs`, `t13_pipe.rs`); both received the same change. `t16_campaign.rs` uses a null stdin and was not affected.

Production is not affected: the helper deliberately treats stdin EOF as an emergency-stop trigger, never as evidence about another process, and the supervised runner never infers death from `kill` returning (it waits for an OS exit observation and verifies identity).

### Repository registration

One explicitly named path. The path and the repository's Git common directory must both resolve strictly inside the configured disposable root, which must itself be a private (`0700`) directory at least three levels deep. A symlink leading out, a linked worktree of an outside repository, the root itself and traversal are refused. Registration goes through the unchanged `register_local_repository`; worktree ownership and isolation code is untouched.

### Feature bundle import

One PRD, one ADR, a one-step execution plan and its validation plan. Import uses the same artifact and review-document commands as any edit and creates drafts only. The core requires an approved PRD before an ADR can exist and both before a plan, so the bundle is sent again after each human decision and advances one stage at a time. The validation plan is stored as its own reviewable document and needs its own approval; the plan binds its digest. A bundle that differs from the imported drafts is refused rather than merged. Approvals are given only through the existing exact-revision `HumanDecision`.

### Start

`Start` carries five identities. The executable, its arguments and its environment come only from the `CodexAdapter` built from the helper's start-up configuration; a frame with any extra field is refused. Refusals that can be known beforehand happen before anything is committed. Acceptance is one writer transaction; then: owned worktree, seal, scheduler reservation with worktree binding, `LaunchSpec` from durable state, `CodexAdapter::prepare_launch`, existing worker registry (issue journal, supervised launch, settlement). The boundary guard now forbids the helper from calling `ProcessLaunch::from_spec`, `Supervised` or `exec_argv` directly.

Duplicate prevention has four layers: a receipt for the command identity short-circuits to "not repeated" in any epoch; an active worker refuses a new Start; acceptance refuses a step that was ever reserved and any unfinished attempt; and the unchanged issue journal refuses a second launch of an attempt.

### Recovery resolution

The four P1-11 choices are exposed as they are. The digest of the helper's current inspection must be named, the core re-checks the durable facts, and the core alone decides which choices the evidence offers. The helper re-inspects after every resolution.

## Security guarantees

- **No arbitrary process execution through IPC.** No command has an executable, argument, environment or directory field; payload field sets are exact. The only launch path is adapter → `Service::launch` → the unchanged P1-09 launch.
- **No real Codex execution, credential access or network inference.** Tests configure a private copy of `jojo-codex-fixture`. The source scan finds no reference to the installed CLI or its state.
- **No duplicate launches.** See above; tested with replay, a lost response, a second command and a crash after issue.
- **No unsafe termination.** No signal code was added. The stop plan for the adapter is the existing TERM-then-KILL plan with the accepted budgets.
- **No unauthorized repository writes.** Registration is confined to the disposable root; the run happens in a Jojo-owned worktree; the sample repository's status and HEAD are asserted unchanged after a run.
- **No bypass of approval or recovery gates.** Import never approves; Start re-reads all four approvals inside its transaction; open admission is not approval; a human choice never replaces OS evidence; quarantined claims are released only by the existing core path.
- The Rust core remains the authority: every refusal the GUI shows is the helper's answer.

## Deviations from the plan text, and limitations

1. **"T15 reproduced with protocol commands only" is met for the slice, not for all of T15.** T15 mixes Claude and Codex steps, several steps and a validator. This milestone drives one Codex step from registration to a settled result through protocol frames only. Multi-step plans, Claude and validation are outside it (validation is P2-03).
2. **Bundle import is staged across approvals**, because the core does not allow a plan to exist before its PRD and ADR are approved. One bundle, sent up to four times.
3. **After an interrupted or failed run, Start stays refused on that data root.** The core keeps a non-successful earlier-epoch attempt as a recovery subject until a reviewed continuation exists, and continuation launches are not offered by this protocol. The run can be held, validated and settled, but the step cannot be started again; a fresh data root is needed. This is fail-closed and will matter for the P2-04 rehearsal.
4. **A crash between Start acceptance and scheduler reservation** leaves an owned worktree ticket whose claim is quarantined and is not a recovery subject. A later Start for that repository is refused ("worktree administration unavailable"). Nothing runs and nothing is lost, but there is no protocol command to clear it.
5. **Live-process recovery is tested at the storage level only** (existing T11). At the protocol level the tests cover an unknown process state (Hold only) and a proven-absent one.
6. **The launch that runs under `Start` is not exercised through the real helper binary inside the gate**: the gate's OS sandbox cannot execute the system `ps` the helper uses for process identity, and no inspector override is exposed on the helper command line (deliberately: it would be a configurable executable). Start-to-settlement is tested in-process through the production `Service`; the real binary is tested for negotiation, refusals and the reviewed start.
7. **The prompt template is code, not a reviewed document.** It wraps the approved PRD rendering, ADR text and validation scope in fixed headings.
8. **The disposable-root rule is structural** (private, three levels deep). It cannot know that a directory is truly disposable; choosing it is the launcher's responsibility.
9. **GUI controls take identities typed by the human.** There is no browser for imported artifacts, and registration and import have no GUI control (protocol only); both are outside "minimal Start and recovery controls".
10. All P2-01 uncertainties about the real Codex CLI remain.
