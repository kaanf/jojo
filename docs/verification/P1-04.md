# P1-04 — Human approvals and invalidation

Result: **PASS — GO for P1-05 implementation. P1-05 has not started.**

Implemented in `crates/jojo-storage/src/approvals.rs`, with migration 3 in the existing SQLite database and invalidation hooks in existing artifact/question transactions. No mutable approval flag or additional database.

Human approve/reject/revoke commands use a distinct, non-deserializable host entry point. Tests explicitly identify fake human origin. Decisions preserve subject revision, canonical/content hash, displayed-content hash, review-bundle hash, upstream decision IDs, human identity, command receipt and event sequence. Review bundles also bind clarification revisions. Prior decision sequence participates in CAS, preventing competing decisions against the same displayed review. Identical command retries replay the receipt; separately submitted duplicate decisions fail.

ADR revisions bind an approved PRD decision; plan revisions bind applicable PRD and ADR decisions. Applicability is derived recursively. All three gates and exact parent relationships are required for attempt reservation and checked again before STARTING. Rejection remains available for incomplete drafts, and revocation remains available when upstream bindings are stale.

Artifact, displayed-content, question/answer and decision changes invalidate dependent applicability in the same transaction and persist stop intent for affected attempts. Cancellation/stop intent survives reapproval and restart. Late or previously sealed results remain byte-identical but become inapplicable. SQLite triggers prevent updates/deletes of decisions, review documents, stop intents and sealed results. Fake provider events, including forged event names and Markdown checkboxes, cannot insert human decisions.
