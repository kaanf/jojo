# P2-04.1 verification — orphan process safety

Result: **GO for requesting one supervised P2-05 attempt**, conditional on `verification/p2-04.1-result.json` recording `passed: true` and `p2_05_single_supervised_attempt: GO` with matching source hashes. This authorizes nothing. No Git repository was initialized, nothing was pushed or merged, and the installed Codex CLI was not located, read or executed.

## The finding

P2-04 showed that when `jojo-helper` is killed, the agent it launched keeps running, unsupervised, until it ends by itself ([P2-04 verification](P2-04.md), gap 1).

## Root cause

- The helper starts the agent as its direct child in a new process group and keeps that child unreaped. The unreaped child is its *lifetime handle*: as long as it holds it, the PID and the group ID cannot be recycled, so signalling the group is safe. Every stop (Cancel, Quit, GUI crash, deadline) is the helper signalling through that handle.
- The handle lives in the helper's memory. When the helper dies it is gone, and macOS has no mechanism that tells a child its parent died (there is no parent-death signal, and the agent's process group is unaffected). The agent is re-parented to `launchd` and continues.
- The core then, correctly, refuses to act: a later helper has only recorded numbers, and "inspection is not a lifetime handle". So the state was held safely, but nothing ended the process.

Reproduced with fixture agents only: `p2_04_1_without_a_guard_the_agent_outlives_a_killed_supervisor` (the supervisor is killed with SIGKILL; three seconds later the OS still shows the agent alive).

## Options considered

| Option | Verdict |
|---|---|
| Parent-death notification in the child | Not available on macOS without code inside the agent. The agent is an unmodified third-party binary. |
| Rely on the agent failing when its output pipes close | Works only for agents that write and do not ignore the error. A silent or stubborn agent runs on (this is exactly the P2-04 fixture). Not a guarantee. |
| Watchdog outside the agent's group that signals recorded PIDs after re-verifying them | Rejected. Check-then-signal on a number is the pattern the architecture forbids; it would weaken "never signal without a lifetime handle". |
| Supervisor between helper and agent (the agent becomes a grandchild) | Reliable, but changes what the helper's direct child is: recorded identity, exit status, argv evidence and the stop path would all move. A larger change than the problem needs. |
| **Guard inside the agent's process group, with a lifeline pipe** | **Chosen.** The launch of the agent is byte-for-byte unchanged, and the guard's own membership is a lifetime handle on the group. |

## Selected approach

For every process group it launches (the agent of a Start, and the command of a Validate, which runs candidate code), the helper starts a second instance of its own executable, `jojo-helper --agent-guard <leader pid> <ps>`:

- **inside that process group** (`process_group(<leader pid>)`, while the helper still holds the unreaped leader), with a cleared environment;
- with a pipe on standard input whose only write end is held by the helper.

When the helper ends for any reason, including SIGKILL, the kernel closes the pipe. The guard sees end-of-file and:

1. verifies from the OS that its own process group is the leader it was given, and signals nothing otherwise;
2. sends TERM to the leader, waits up to 2 seconds for it to go;
3. sends KILL to the group, which ends every member and the guard itself.

Why this is safe with respect to identity: a process group exists as long as it has a member, and the kernel does not give a new process a PID that is in use as a process-group ID. The guard is a member, so while it lives the group ID is the group the helper created, and the leader's PID can only be the original leader or nothing. The guard never signals a number it merely looked up.

While the helper lives nothing changes: it remains the only supervisor and the guard takes no part in a normal stop. When the group is confirmed stopped, the helper writes a release byte and the guard exits without signalling. A TERM or INT that the helper sends to the group also ends the guard; the helper replaces it on its next poll while the group still has members. If a guard cannot be kept alive (16 replacements), the run is stopped as an inspection failure. If the guard cannot be armed and observed inside the group at launch, the launch is killed at once and reported uncertain. The guard is excluded from the agent's tree: it is never recorded as a descendant and does not keep a finished run from being reaped.

Recovery is unchanged. After a helper death the next helper inspects as before; the group is now empty, so the choices are offered at once and the run settles as `Interrupted — helper_lost_recovered`. If the guard is still within its grace period the group has live members and everything is held, as before.

### Evidence about macOS behaviour

Observed on this machine (Darwin 27.0.0), not assumed:

| Question | Observation |
|---|---|
| Does anything end a child when its parent is killed? | No. Reproduced by test and by the P2-04 rehearsal. |
| Is end-of-file on a pipe delivered when the only writer is killed with SIGKILL? | Yes, at once. In the rehearsal the agent was gone 0.02 s after the helper was killed. |
| Can a process be started inside an existing process group, and does KILL to that group reach all members? | Yes (`process_group(pgid)`; guard tests). |
| Is a PID reused while it is still a process-group ID? | See `verification/p2-04.1-dev/pid-reuse.log`: a group's leader was reaped while a member lived, and the PID counter was driven past that number. |
| Does the kernel end an orphaned group? | Only if a member is *stopped* (the POSIX rule: HUP and CONT to every member). Seen once, when a frozen guard was tried as a way to simulate guard loss: the agent ended when the helper was killed. A running group gets nothing. Not usable as a mechanism. |

## Guarantees

| Process | Guarantee after the helper dies |
|---|---|
| The agent itself (group leader), any agent | TERM, then KILL within about 2 seconds. KILL cannot be ignored. Verified with a fixture that ignores TERM and INT. |
| Descendants that stay in the agent's process group | Killed with the group, also when the agent itself has already exited. Verified. |
| A cooperating agent's descendants outside the group | The TERM gives the agent up to 2 seconds to stop them itself. Nothing enforces it. |
| Any descendant that left the group (own group or session) | **Not covered.** Recorded if the supervisor saw it, shown by recovery, never signalled. Verified as a limit. |
| Validation command and its group | As for the agent. Verified in the rehearsal. |

## Remaining risks

1. **Processes outside the agent's group are not reached.** Whether the real Codex CLI puts its tool processes into their own groups is unknown. If it does and is killed rather than stopped gracefully, they can survive. The operator checklist has the human record such processes during the run.
2. **The guard is an ordinary process of the same user.** The agent, or anything else running as the user, can kill or stop it. A lost guard is replaced while the helper lives. If helper and guard are both gone, the P2-04 behaviour applies: the agent runs on, everything is held, and ending it is a human action.
3. **A frozen helper is not a dead helper.** A helper that hangs or is stopped keeps the pipe open; the guard does not fire.
4. **A short unguarded window** exists after the helper sends TERM or INT to the group, until the guard is replaced (one poll).
5. **Up to 2 seconds** pass between helper death and KILL for an agent that ignores TERM.
6. **Pipe inheritance race.** macOS cannot create a pipe close-on-exec atomically. A child spawned by another helper thread at that instant could inherit the write end; the guard would then fire when that child exits.
7. **Nothing is recorded about the guard's action**, because the recording process is dead. The next helper settles from OS evidence.
8. The guard relies on `/bin/kill` and `ps`, as the supervisor already does.
9. All P2-04 gaps other than gap 1 stand: no restart on a used data root, the Start-to-reservation crash window, digests instead of text in the Review tab, and everything unknown about the real CLI.
