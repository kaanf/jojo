### The sample

`python3 scripts/p2_04_sample.py repository --disposable-root <root>` creates `<root>/slugify-sample` with `slugify.py` (a stub that raises `NotImplementedError`), `test_slugify.py` (eight standard-library tests) and one commit on `main`. Author, committer, dates and message are fixed, so the commit is always `45147111b537d1965241c4d2b40e32ad9b740ea9`; the generator refuses to report any other. It refuses a root that is not private, is fewer than three levels deep, or lies inside this project or any Git repository, and it never reuses an existing directory.

The bundle: write scope `slugify.py`; baseline `test_slugify.py`; validation command `/usr/bin/python3 -m unittest -q`. The rehearsal appends one clearly marked `fixture: <scenario>` line to the ADR, which is how the fake executable is told what to do; the bundle for a live attempt has no such line (tested).

### How a scenario runs

Each scenario creates its own directory: a disposable root with a freshly generated repository, a data root, a worktree root, a private copy of the fake executable and a Codex home holding only a random canary. Nothing is reused and nothing is deleted.

| Step of plan section 4 | Interface used |
|---|---|
| 1 Register the repository; 2 import the bundle | protocol frames to a real `jojo-helper --serve` over pipes. The app has no control for these (P2-02 limitation 9) |
| 3 Review and approve PRD, ADR, validation plan and plan | the app's Review tab entry points, one exact revision each. Import is staged by the core, so helper and app sessions alternate three times |
| 4 Start | the app's Recovery (reviewed start) and Start entry points; one Start |
| 5–6 Supervised run and settlement | the helper the app started; observed through the Candidate tab's model |
| 7 Diff and scope verdict; 8 host validation; 9 display; 10 Accept or Reject | the app's Candidate tab entry points |
| Quit, confirmation, recovery choices | Cmd-Q through the main menu, the confirmation handlers, the Recovery tab entry points |

Afterwards a separate protocol session reads the helper's own answers (candidate, changed paths, launch effects, attempts, recovery subjects) and the harness compares them with what the app displayed. The database is never opened.

## Unresolved gaps

1. **A helper crash leaves the agent running.** By design the core never signals a process it has no lifetime handle for, so after a helper crash the agent runs unsupervised until it ends by itself. Everything else holds: the state is quarantined, only Hold is offered, nothing can be settled, validated, accepted or started, and Quit refuses to report a clean stop. In the rehearsal the fake agent is silent and ends after 25 seconds. A real Codex could keep writing to its owned worktree and using the provider for the rest of its turn. This is the stop condition "orphaned process"; ending the process is a human action on the exact PID the Recovery tab shows (operator checklist, section 8). Closing this in software means a supervising process that outlives the helper, or a signal on re-verified identity — an architectural decision that was out of scope here.
2. **Only the root process is covered.** The fake agent starts no child. Recovery inspects the recorded process and its group; a descendant that left the group would not be seen. The real process tree is unknown.
3. **No restart on a used data root** (P2-02 limitation 3, deferred by decision). Every non-successful run remains a recovery subject and Start stays refused there; a succeeded step is refused as a duplicate. A further attempt needs a fresh data root and a new authorization.
4. **A crash between Start acceptance and reservation** (P2-02 limitation 4) still has no resolution command. Not exercised.
5. **The Review tab shows digests, not text.** The human reads the documents in `scripts/samples/slugify/` and relies on the helper refusing changed content. The app also has no registration or import control, so approvals need three app sessions with imports in between.
6. **The fake executable is not Codex.** Event shapes, sandbox behaviour, reaction to SIGTERM and to closed pipes, and sign-in behaviour of the real CLI remain unknown (all P2-01 uncertainties stand).
7. **Unsandboxed steps.** The rehearsal and the real-helper regression run outside the OS network sandbox because the helper needs the system `ps`. They are offline by construction (fixture executable, no network code), not by OS enforcement. The validator's own network denial is in force and visible in every report.
8. **An authentication failure is not classified as such.** It is recorded as `Failed — provider_error`; the reason is only in the agent output.
9. **The source repository gains a Jojo-owned branch ref** (`jojo/<attempt>`) and a linked-worktree registration. Existing P1-07 behaviour; `main`, `HEAD`, the index and the working tree are untouched.
10. Validation directories, worktrees and rehearsal roots are kept; nothing prunes them.
